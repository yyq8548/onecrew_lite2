# OneCrew 合并与部署流程

维护日期：2026-10-15。适用于本工作区后续开发调整、GitLab 合并、客户端发布和云端部署。

## 1. 发布原则与范围

标准顺序：读取最新主分支 → 功能分支开发 → 验证 → GitLab MR → 合并主分支 → 固定发布提交 → 构建和验收 → 发布 → 线上验收 → 更新记录。

已打包成品的发布顺序：接收包和来源记录 → 校验包 → 从共享主分支建立发布分支 → 提交发布清单与记录 MR → 合入共享主分支 → 核实合并提交 → 上传并校验包 → 切换线上清单 → 客户入口验收 → 同步结果。已经拿到安装包也必须先完成发布清单 MR 的合并，再切换线上下载。

正式发布只能使用已经合入指定主分支的确定提交。个人功能分支和长期 Lite 集成分支用于开发或集成。若 MR 先进入集成分支，必须继续合入指定主分支，才能进入正式发布。

| 修改内容 | 仓库与主分支 | 实际交付对象 |
|---|---|---|
| onecrew_lite 本体、本地页面、搜索、登录、邮件、Codex 接入 | 公司 `onecrew_lite/onecrew_lite`，主分支 `main` | 分平台客户端安装包及下载清单 |
| Access 登录、授权、安装提示词、下载接口、发布状态与内部后台 RPC | 公司 `onecrew/onecrew-access`，主分支 `onecrew` | Access Worker 和账号页面静态资源 |
| 公开官网 | `onecrew-site`；执行前核实其默认分支 | 官网构建产物 |
| Sync 服务、管理后台 | 各自所属仓库；执行前核实发布分支 | 对应 Worker、页面或服务 |

每次工作开始重新核对远端和主分支。表中的已知分支如有变更，以经确认的公司约定为准，并更新本文件。其他项目的 `pre_release`、`online_test` 仅作为示例，当前项目有明确环境和分支约定后才采用。

Access 是 Lite、Pro、账号及后台接口共用的服务。每次部署都会发布整个 Worker 和对应静态资源，必须保留同事已合并的功能、变量、绑定和数据库迁移。

沟通中的“main／主分支”应落实为具体仓库和实际分支名。客户端仓库当前为 `main`，共享 Access 仓库当前为 `onecrew`。Mac 和 Windows 可分别维护、构建和交付安装包；共享网站的发布清单及服务修改统一合入 Access 的 `onecrew`。

## 1.1 用户提供已打包安装包时

本次工作仅负责网站分发时，保留提供方的成品包，登记其版本、修订号、源码提交、构建记录、平台、大小、SHA-256、实机验收和签名状态。区分提供方确认与本机独立核实，来源缺少证据时明确记录，不编造源码 MR 或合并结论。涉及修改或重建客户端时，再执行客户端源码开发与合并流程。

1. 校验 ZIP 完整性、包内清单及安装脚本引用的程序哈希；检查当前 Access 清单契约是否接受版本、目标平台和对象文件名。文件名映射必须记录，成品 ZIP 内容保持一致。
2. 获取公司 Access 最新 `onecrew`，从该提交创建功能分支；提交平台发布清单和发布记录，包含包来源、测试、限制及恢复方案。
3. 创建目标为 `onecrew` 的 MR，核查差异和必要检查；确认 MR 为 merged，并获取实际合并提交。没有主分支合并权限时，请维护者合并，停在上传和切换之前。
4. 从已合并提交读取发布清单，保存生产基线和 ETag；上传独立对象，完整回读验证大小和哈希后，条件切换对应平台清单。
5. 验证客户安装入口、中英文指引、下载 HEAD、完整 GET、哈希和后台平台状态，同时核对其他平台与 Pro 保持预期状态。
6. 将最终合并提交、发布时刻、清单哈希、线上验收及恢复入口同步到 MR 和发布记录。

仅发布成品包和清单时，无须重复构建客户端，也无须重部署未发生代码或配置变化的 Worker。网站实际读取 R2 清单，GitLab 合并不会自动更新 R2；两处状态必须分别确认。

用户说“替换线上包”“已经验收”或“继续”，不代表取消先合并再发布的要求。必须遵循已约定流程，只有用户明确修改流程时才调整。

发现安装包已先行上线而 MR 尚未合并时，如实标记“下载已上线，发布清单 MR 待合并”。补齐 MR 后核对主分支与实时生产清单；内容一致则保留现有对象并复验，无须制造下载中断或重复切换。不得把补交记录描述为原先已按顺序发布。

## 2. 确认任务与授权

建立本次发布记录，列出需求、任务编号、受影响仓库、目标平台、交付物、验收标准和停止边界。提交信息、分支命名遵循当前公司约定；历史任务使用 QB-3448，新任务核实对应编号。

分别记录推送分支、创建 MR、合并、上传产物、切换下载清单、数据库迁移和生产部署的授权范围。已有明确授权继续有效；创建 MR 不自动代表获准合并或部署。缺少生产操作授权时，先完成可审阅的代码、验证和发布清单，再申请一次具体审批。

完成条件：每项修改都有所属仓库、目标和负责人；生产操作范围可明确判断。

## 3. 获取最新代码并开发

1. 检查工作区状态及项目 AGENTS.md，保留用户和其他任务的未提交修改。
2. 获取远端最新引用，核实默认分支、待合并 MR、同事最新提交和当前生产来源。
3. 从对应最新主分支建立功能分支。已有分支继续开发时，先检查与目标主分支的差异和冲突。
4. 修改共享接口时检查直接调用方；涉及 Access 时核对 Lite、Pro、设备管理和后台接口。
5. 将修复限制在需求范围，保留现有账号、数据、授权校验和外部操作确认要求。

完成条件：基准提交已记录，改动范围清楚，同事改动得到保留。

## 4. 验证并创建 MR

先复现问题，运行针对性回归，再执行仓库规定的相关类型检查、测试、构建和差异检查。使用真实实现验证；离线检查与真实设备验收分别记录。

测试失败必须说明失败项和影响，修复范围内问题后重验。基线失败需有独立证据；不能因标注“原有失败”就自动视为通过。影响发布正确性的失败必须解决；需要接受的已知限制应进入明确审批。避免为修复格式检查而批量修改无关源码。

MR 必须包含：

- 关联任务、具体问题及修改后的行为。
- 源分支、目标主分支；多个仓库之间的 MR 链接与先后关系。
- 涉及 Lite、Pro、客户端、账号服务和后台接口的准确范围。
- 验证命令、结果、日志位置、平台与未完成验收项。
- 配置或数据库迁移要求、兼容性、部署步骤及恢复方案。
- 若涉及安装包，注明包来源、版本、修订号和对应源码提交。

完成条件：MR 可供审核，验证证据完整，尚未发布的状态明确。

## 5. 合并并固定发布来源

1. 确认 MR 审核和所需检查通过，并具备合并授权。
2. 合并到对应主分支；通过集成分支的改动继续完成主分支合并。
3. 在 GitLab 网页完成合并后，本地切回对应公司主分支并执行 `git pull --ff-only`，确认 MR 为 merged，相关变更确实在主分支中。客户端对应公司 `main`；共享 Access 对应 `onecrew`。远端名称以当前仓库配置为准，避免拉取同名的个人 GitHub 分支。
4. 固定拉取后的完整主分支提交 SHA，使用干净的构建目录。若本地主分支名称因多远端或工作树共存而不同，记录它实际跟踪的公司远端分支；禁止从个人功能分支直接部署。
5. 发现主分支继续前进时，核查新增变更的部署关系。需要包含新改动时重新固定提交并补做受影响验证。
6. 合并后构建必须对应合并结果。若复用已有候选包，须证明其完整构建输入与主分支相应输入一致，包括源码、锁文件、资源及构建配置，并在记录中明确包的实际构建提交；无法证明则重新构建。

完成条件：可以从已合并源码重现产物，源码、产物与验证证据对应。

## 6. 构建并验收 onecrew_lite 客户端

从客户端主分支的发布提交分别构建受支持的 Mac、Windows 包。命名统一使用 `onecrew_lite`，各平台包准确标识产品版本、平台、架构和包修订号。每次修订使用新文件名，保留历史产物。

记录每个包的：源码提交、版本、包修订号、构建环境、文件名、字节大小、SHA-256、签名与公证状态、附带插件或服务版本。

按受影响范围验证：全新安装、已有安装升级、账号和数据保留、服务启动与重启、浏览器授权、Codex 加载、本次修复、卸载或恢复路径；涉及共存时增加与标准版共存检查。安装本体和接入 Codex 分步记录。

Mac 和 Windows 各自取得原生验收证据。离线测试或跨平台编译不等同于实机通过；缺少某个平台环境时记录待办并停止该平台的发布切换，除非已有针对该限制的明确发布授权。仅修改 Mac 时保留 Windows 已发布包，不宣称 Windows 已包含同样修复。

完成条件：每个平台均有准确的产物来源和验收结论；签名限制得到如实说明。

## 7. 审批并发布

生产操作前准备具体清单：仓库提交、MR、安装包与哈希、目标 Cloudflare 账户与服务、R2 对象、即将变更的清单、迁移、验证结果、影响范围和恢复入口。已有授权覆盖时直接执行；否则在此提交审批。

发布前重新读取生产状态，保存当前 Worker 版本、变量配置摘要和下载清单及其 ETag。敏感值不进入 Git、文档或日志。若线上状态已被同事更新，先比较差异并调整本次发布，避免覆盖。

按依赖顺序执行：

1. **安装包上传**：上传至新的 R2 对象，核对远端大小和内容哈希，保留现有下载指向。
2. **服务兼容准备**：新包依赖新接口时，先发布兼容现有客户端的服务。涉及多个服务时记录具体依赖次序。
3. **数据库迁移**：仅执行本次必要且已获授权的迁移；检查备份和新旧代码兼容性。使用新增迁移，保留已发布迁移文件。
4. **服务部署**：从已固定的主分支提交构建，核实生产账户、域名、Worker、D1、R2 和服务绑定后执行仓库正式发布命令。
5. **下载清单切换**：确认产物和服务准备就绪，再更新对应平台清单或版本指向。使用服务支持的条件写入；无法原子更新时明确维护窗口及恢复步骤。
6. **关联页面发布**：有官网或后台页面修改时，从各自已合并提交独立部署，验证与服务接口兼容。

Access 当前部署入口为 `development/deploy.mjs`，由 package.json 的 deploy 脚本调用。执行前读取最新脚本及配置。该入口现有检查不覆盖“已合并主分支”和完整测试，操作者必须完成本流程前述检查。

完成条件：每次远端变更均有执行结果、对应提交及生产版本记录。

## 8. 从客户入口验收

- 官网到 Access 的跳转、登录、体验审批和授权可用。
- 安装提示词指向正确产品，私人链接按要求保护，授权与过期行为正确。
- 实际下载的包与发布记录的大小、哈希、平台和版本一致。
- 安装或升级后报告正确版本，Codex 能加载，账号和数据得到保留，本次修复通过。
- 后台发布状态展示实际可用平台；Pro、设备管理和受影响的后台接口回归通过。
- 验证涉及邮件、消息或其他外部写入时，单独检查既有授权范围，禁止把发送行为当成隐含验收步骤。

网站部署完成不代表客户端包已经更新；上传安装包不代表下载清单已切换；MR 合并不代表已部署。最终记录分别填写实际状态。

完成条件：客户实际入口取得的产物和运行行为与本次发布目标一致。

## 9. 异常恢复

下载包异常时，将对应平台清单恢复到已验证的旧产物；其他平台保持原状态。服务异常时，使用已记录且与当前数据库兼容的历史部署版本恢复。恢复前重新读取生产状态，保留同事期间发布的必要更新。

数据库变化先判断兼容性和数据损失风险，使用经过验证的恢复或追加修复方案。代码需要修正时通过文件编辑、测试和新 MR 处理，遵守禁止 Git 回滚代码的工作区规则。

恢复后重新执行受影响的客户入口验收，记录恢复对象、原因、时间和实际状态。

## 10. 发布记录与交接模板

每次发布在项目文档或工作区 outputs 中建立独立记录，包含以下字段：

| 字段 | 必填内容 |
|---|---|
| 需求与授权 | 任务编号、修改范围、操作授权、验收标准 |
| 源码 | 仓库、目标主分支、MR、完整发布提交 SHA |
| 产物 | 分平台版本、修订号、构建来源、文件名、大小、SHA-256、签名状态 |
| 验证 | 命令、结果、日志、实机环境、未完成项及其发布决定 |
| 生产状态 | Cloudflare 服务、Worker 版本、R2 对象、清单版本或 ETag、必要迁移 |
| 过程状态 | 已编码、已验证、已提交、已合并、已上传、已切换、已部署、已验收分别填写 |
| 恢复 | 旧 Worker 版本、旧清单与包、数据库兼容性、恢复验证 |
| 后续工作 | 待办、负责人、阻塞信息和下一步 |

完成发布后更新 MR 和发布记录。跨电脑交接携带源码获取方式、本流程及入口、当前发布记录和所需的非敏感环境说明。

## 11. 维护边界

本文件是工作区发布流程的唯一维护入口。分支、工具和服务配置发生变化时，先核实当前仓库，再更新相关条款。各仓库保留自身具体命令和架构说明；历史发布状态写在对应发布记录中。

这份流程保存在本地工作区，由工作区 AGENTS.md 引用。向公司 GitLab 或其他电脑同步时，应明确把文档和入口一并纳入交接或文档 MR；本地保存不代表公司仓库已采用。
