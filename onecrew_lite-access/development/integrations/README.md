# Mailbox connections on Access

OneCrew's local Node service sends mail and reads Gmail threads and attachments with the provider SDK. Access only obtains and stores the mailbox OAuth grant, tracks the Access user's connections, and gives a validated local device a short-lived provider access token. A mailbox is not a OneCrew login identity: its address may differ from the Access login address, and one user may connect multiple mailboxes.

The panel opens `/integrations/mail/connect?provider=google&expected_user_id=<Access user id>`. `expected_user_id` is optional and is only compared with the active browser session. The page shows the current Access account and requires a click before redirecting to Google. The session user is always the connection owner. If the browser has another Access account, the page blocks the flow and tells the user to switch accounts. There is no desktop authorization request, approval, status polling, or MCP connection endpoint. Google returns to the registered callback the production Access origin plus `/integrations/gmail/callback`.

`GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET` identify this OAuth app; they are separate from Better Auth's `GOOGLE_CLIENT_*` login app. Set both as Worker secrets along with `THIRD_PARTY_TOKEN_ENCRYPTION_KEY`, an independent 32-byte base64url key. Never store secret values in config, fixtures, or logs. The callback URL must be registered exactly. `openid-client` 6.8.8 performs discovery, PKCE, state and nonce checking, code exchange, ID-token signature/issuer/audience validation (with `enableNonRepudiationChecks` for JWKS verification), refresh, and revoke. The Google adapter requests `openid`, `userinfo.email`, `gmail.send`, and `gmail.readonly`; the connection records actual granted scopes. Send-only and read-only grants are usable with reduced capabilities. Outlook is reserved in the provider-neutral contract and returns `not_supported` in production.

Migration `0014_mail_oauth.sql` adds `mail_connection` and `mail_oauth_transaction`; it has not been applied remotely. `mail_connection` holds one encrypted credential and actual scopes per Access owner/provider/mailbox subject, with status `connected`, `reauth_required`, `disconnecting`, or `disconnected`. `mail_oauth_transaction` contains only one short-lived state hash, owner, encrypted PKCE verifier, nonce, expiry, and consumption time. Disconnect atomically blocks token issuance and deletes the owner/provider’s outstanding transactions; callbacks must verify their transaction is still present in the same D1 statement that writes a connection. The active `(provider, provider_subject)` grant is unique across Access users; disconnected history does not block another owner. Neither table has foreign keys. Migrations 0001–0013 remain immutable. The new `0015_retire_tkone_integrations.sql` migration drops the five historical TkOne integration tables if they exist. It does not touch Better Auth accounts, devices, distribution, or the two mail tables. The five TkOne tables were dropped directly from remote D1 with this SQL and verified absent, with no foreign key violations. Migration 0014 remains unapplied remotely; 0015 has not been recorded in the migration registry.

Machine API base: `/api/desktop/integrations/mail/v1`, envelope `onecrew.mail` version 1. `GET /connections` lists the owner's connection metadata, `GET /connections/{id}` reads one, `POST /connections/{id}/access-token` returns a provider access token with expiry, scopes, and email, and `DELETE /connections/{id}` disconnects. Every call validates the existing Sync credential through `SYNC_CREDENTIAL_VERIFIER` and then checks the corresponding Access device and pairing. The browser and MCP cannot obtain access or refresh tokens. No mail body, attachment, thread, or send operation passes through Access.

Disconnect first marks the connection `disconnecting`, so it cannot issue more tokens and a reconnect to the same provider is blocked while revocation is unresolved. Access then asks the provider to revoke the retained refresh grant. Only a confirmed success clears ciphertext and marks `disconnected`; timeout, 503, or other unconfirmed responses leave the same token available for a repeated DELETE. A Worker interruption likewise leaves `disconnecting`, and the user can repeat DELETE without an operator changing database state. Concurrent retries may issue the same idempotent revoke request. Each completion updates only its original connection ID and ciphertext; a later confirmed reconnect uses a new ID and keeps the old `disconnected` row. Google’s 200 response may take time to propagate, and a timed-out provider request cannot be canceled by a database condition, so a late external response remains an upstream uncertainty. `invalid_grant` on a later refresh moves an active connection to `reauth_required`; insufficient mail scope only reduces capabilities and does not revoke the grant. An already active or `reauth_required` mailbox reauthorization keeps its connection ID; after confirmed disconnect it receives a new ID.

The browser returns only HTML status and mailbox address. Callback state is single-use and expires in ten minutes. No callback automatically closes a window or opens a local tab. Apply `0014` and deploy only in a separately authorized rollout. The mail integration tests exercise the real `openid-client` against local mocked provider network responses, including signed ID tokens.
