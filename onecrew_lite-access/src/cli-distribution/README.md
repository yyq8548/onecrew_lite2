# CLI installation distribution

Access serves private raw CLI artifacts through its `RELEASES` Worker binding.
Publish all three binaries and verify full GET readback before publishing
`releases/<version>/cli-manifest.json` and setting `CLI_RELEASE_VERSION`.
The manifest uses `schema_version: 1`, `product: onecrew-cli`, a numeric version,
and exactly three canonical target assets with object key, size, and SHA-256.
Access validates the manifest and all three objects' metadata. An absent or
invalid version pin disables the install gateway, including pending downloads.

## Stateless browser-to-agent handoff

New installation credentials are not stored in `cli_install_ticket`, D1, KV,
or another per-link registry. The existing user and distribution entitlement
remain authoritative and are read on every authorization. This is stateless
link validation, not a replacement for account authorization.

`credentials.ts` derives an AES-256-GCM key from the existing independent
`RELEASE_LINK_SECRET` using HKDF-SHA-256. The derivation is scoped to the CLI
credential protocol and configured Access origin. A fresh 96-bit nonce and
authenticated protocol identifier protect each strict, versioned payload.
Encrypted contents include only the account ID, entitlement revision, issuance
and expiry times, credential purpose, and (for downloads) version/manifest hash.
The key is not shared directly with the legacy Desktop link encryption protocol.
Missing or invalid key configuration fails with 503; it is never treated as an
expired cookie. Rotating the root secret invalidates outstanding credentials.

Credentials are bounded `v1.<base64url>` URL segments. The HTTP allowlist, frontend
URL schema and shell-template renderer all recognize the same bounded format.
No account session, pairing secret, or R2 API credential is placed in the URL.
Do not log or share credentials, cookies, prompts, or rendered scripts.

### Browser recovery

`GET /api/cli/install-links` requires the normal verified browser session and
active entitlement. It returns `{link: null}` or the still-valid entry belonging
to that account from the `__Host-onecrew-install` cookie. It never mints a new
credential. Invalid, expired, other-account, or old-revision cookies are cleared.

`POST /api/cli/install-links` additionally requires the exact Origin, JSON
content type and an empty object. It reuses a valid entry from that cookie or
issues a new 24-hour entry after checking current release availability.
Responses contain `{url, expiresAt, prompt}`. The prompt is generated by the
current backend deployment rather than reconstructed by the frontend.

Both browser endpoints render the prompt using `Accept-Language` (zh-CN or
en-US, defaulting to zh-CN). The absolute URL inside the prompt carries that
choice as `?lng=...` so an agent fetching it without a language header receives
the same language. The entry page prefers a supported `lng` value, otherwise
uses `Accept-Language`, and returns `Content-Language`. Changing the page
language restores a translated prompt without replacing the credential or
extending its expiry. The API's relative `url` and cookie remain language-free.

Both prompts ask the agent to identify the target AI client before choosing a
connection route. Codex uses `plugin install`; other MCP clients use `setup`
and launch the returned `mcp --stdio` configuration themselves. `serve` opens
the local service and webpage, not an MCP transport. Returned next actions and
connection options apply only to the matching client. If the client is unknown,
the agent can finish CLI installation and required login, but must ask for the
target before changing client configuration. Installation/configuration and a
verified live client connection are reported separately.

Environment selection distinguishes the user's target computer, the machine
reachable by execution tools, and the AI client's integration capabilities.
Shell OS results from a cloud sandbox, VM or WSL are not evidence of the user's
desktop OS. Before selecting an installer, the agent must establish the target
and tool connection to it. Missing local execution access is not an unsupported
target OS; missing local stdio support is a separate client capability limit.
The short account prompt includes this rule so a sandbox result cannot send the
agent into the wrong platform flow before it reads the full guide.

Both the short prompt and full guide require agents to request narrowly scoped
sandbox/tool permission through the execution tool's supported approval mechanism
and wait for the result. Task authorization does not waive tool approval. Denial
stops that step, not a retry through another shell or agent. Permission approval
cannot provide a missing connection to the target computer; non-permission errors
and unknown command effects must be diagnosed rather than blindly retried.

The entry responds with `text/markdown`: one localized guide covers installation,
client configuration, and recovery. The displayed deadline belongs to the scoped
download URLs, not the longer-lived entry. On `download_refresh_required`, reopen
the original entry for new URLs; if that entry has expired, obtain a new prompt
from Access. Scripts never receive the longer-lived entry credential.

Current bootstrap installers preserve the CLI's JSON on stdout and write progress,
client-selection reminders, and failures to stderr. Legacy output remains key/value
text. Download failures distinguish access denial, links requiring refresh, and
temporary network/server errors without printing credential-bearing URLs. Neither
script installs a client plugin or edits client configuration. `setup` continues
to return MCP JSON; the Markdown guide explains how the agent should apply it.

The Windows guide uses native PowerShell 5.1+ and `powershell.exe -NoProfile
-NonInteractive -File`, with PowerShell environment variables and quoted paths.
It does not prescribe execution-policy bypasses. The installer uses
`Start-Process -PassThru` with separate redirected streams, explicit native exit
codes, and `Wait-Process -Timeout` for the command itself. It deliberately avoids
`Start-Process -Wait`, which also waits for descendants such as the local service.
Version checks allow 30 seconds, bootstrap 120 seconds, and service probes share
a 60-second deadline. On timeout only the command started by the installer is
stopped; replacement state can be unknown and must not be reported as rollback.
Failures emit fixed `stage`, `error`, `native_exit_code`, and `cli_installed` fields
on stderr without raw exception details. The guide stops blind reinstall/manual
replacement and leaves browser authorization or client trust to the user.

Microsoft references: [PowerShell.exe](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1),
[Start-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process?view=powershell-5.1),
[Wait-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/wait-process?view=powershell-5.1).
Run `node --test development/cli-installer-windows.test.mjs` on Windows for native
PowerShell stream, quoting, exit-code and timeout coverage. It is skipped on other
operating systems; source checks are not Windows execution validation.

The cookie is host-only, Secure, HttpOnly, SameSite=Strict, Path=/, with a maximum
age no longer than the credential's remaining lifetime. Reusing an entry does
not extend its expiry. Clearing browser cookies loses browser recovery, but
does not revoke an already-copied credential. No private link is stored in
localStorage or sessionStorage. The frontend keeps the returned value only in
memory and ignores responses for a component that has been unmounted.

Refreshing restores a prompt; it does not copy it or create a new link. The
generate action waits for restoration, then creates only when needed. Copying
again reuses the current prompt. Expired entries are replaced only after a
click. Installation expiry is displayed only when an actual link is available.

An edge rate-limit group covers browser issuance/recovery and agent entry/file
reads. Keys contain only the group and connecting IP, never the token. This is
a permissive PoP-local abuse gate, not the old database-enforced one-link-per-
account-per-minute rule. There is no synthetic 60-second UI cooldown; real 429
responses supply the retry delay. Exact global account throttling would require
separate state. Issuing another stateless entry does not revoke older entries.

### Version selection and pinned downloads

An entry at `/cli/install/v1.<credential>` does not contain a release version.
Access validates its purpose, time window, user verification, active entitlement
and revision, then selects the current `CLI_RELEASE_VERSION`. It returns the
current deployment's installation instructions with script URLs under
`/cli/download/v1.<download-credential>/`.

The download credential binds that specific release and canonical manifest hash.
It lasts at most one hour and never beyond the parent entry's expiry. Its
`install.sh`, `install.ps1` and `files/<target>` GET/HEAD routes need no browser
cookie, but recheck user verification, entitlement and revision on every request.
An entry credential cannot access download routes and a download credential
cannot start another installation or restore a browser entry.

Changing the release pin affects the next entry access, not an installation
already selected. Scripts and binaries stay on the same manifest. Replacing or
removing those artifacts fails closed. Reads are retryable until expiry; a link
is not consumed by inspection, HEAD, script download, or binary download.
Permission revocation blocks subsequent requests, not a response already streaming.
Single-link revocation is deliberately unavailable without per-link state.

Private responses use no-store and no-referrer. Browser credential endpoints
also vary on Cookie. R2 stays private behind the same-origin Access gateway;
S3 presigned URLs and public R2 access are not introduced.

## Installer lifecycle

The `.txt` templates in this directory are served by the current Access
deployment. macOS selects ARM/Intel including Rosetta; native Windows PowerShell
supports x64. Both validate file size, SHA-256, native header and exact version.
Before 0.5.22 the legacy replacement/login branch remains available. From 0.5.22
the downloaded candidate runs `__bootstrap-update`, so the old CLI does not need
to support `update`. Updated and already-current results verify service binary
identity and startup/data readiness before success; a mismatched host is stopped
and rechecked. First installation returns login guidance without this postflight.

The installation instructions then require plugin install/reinstall using the
installed CLI, including only legacy OneCrew identity cleanup identified by the
CLI. Plugin installation is not proof of a refreshed MCP session: fully quit
and restart Codex, then verify in a new task. Native Windows execution is a
separate acceptance check from template and cross-build tests.

## Legacy-ticket drain and removal

Keep migration `0010_cli_distribution.sql` unchanged. Existing 43-character
links use the old read-only verifier and remain pinned to their recorded release
until expiry. New routes never insert or update legacy tickets. Each scheduled
run deletes at most 500 expired rows; active rows are retained.

After deploying the cutover, inspect the maximum legacy `expires_at` and wait
until all previously issued links expire. Confirm cleanup has emptied the table
before a subsequent additive migration drops it and a subsequent code change
removes the old verifier/routes and cleanup job. Do not drop the table during
this initial cutover or claim remote cleanup has happened from local tests.

## Authenticated CLI updates and account projection

`GET /api/cli/update` and `/api/cli/update/<version>/files/<target>` retain the
existing installation-credential authentication and current-version selection.
Browser cookies or either install credential cannot substitute for that bearer.
The response is same-origin, no-store and varies on Authorization. A changed
release pin during a direct CLI update returns 409 so the CLI can recheck it.

Account and Admin projections retain `cliRelease: {status, version, targets}`.
The old `cliTicket` projection is removed: browser recovery uses its dedicated
authenticated endpoint and never needs a latest-ticket database lookup.
Existing Desktop publication fields and routes remain separate.
